# HU54: creación de campañas ecológicas institucionales

HU54 publica campañas para miembros de una institución. El formulario es responsabilidad
del frontend; el backend aporta contrato validado, verificación de acceso administrativo,
creación y consultas. No implementa reportes HU55 ni afiliación de usuarios.

## Modelo y arquitectura

Controller → CampanaInstitucionalService → CampanaInstitucionalServiceImpl →
RetoRepository/InstitucionRepository → Reto/Institucion.

La campaña es un Reto de tipo COLECTIVO con institucion_id. Sus campos existentes
titulo/descripcion/fechaInicio/fechaFin/activo representan nombre, objetivo, periodo y
publicación. puntosRecompensa=0; no tiene recomendacionOrigen ni categoría inventada.
No se crea una segunda tabla de campañas ni lógica paralela de progreso/cierre.
El ID de campaña es el ID del reto, reutilizable para HU29 y los futuros reportes HU55.

HU51 ya utiliza usuarios_instituciones con ADMIN_INSTITUCIONAL. Faltaba un rol de
miembro ordinario: se añade MIEMBRO al enum y al CHECK de la base. No se asigna
automáticamente a nadie ni se concede un rol global. Cualquier vínculo válido
acredita pertenencia; solamente ADMIN_INSTITUCIONAL permite crear.

## Autorización y concurrencia

El usuario se obtiene de UserSecurity/JWT, nunca de administradorId del body.
La institución se toma de la ruta. Para crear se bloquea la institución y se valida
el vínculo administrativo con bloqueo compartido, impidiendo cambiar/revocar ese
vínculo durante la transacción. El mismo nombre (sin distinguir mayúsculas y espacios
exteriores) y periodo no puede repetirse en la misma institución. Distintos periodos
o instituciones pueden reutilizar un nombre. El índice único respalda esa regla.

Miembros y administradores pueden consultar campañas de su institución. Usuarios
externos reciben 403. El detalle valida que ambos IDs de ruta correspondan a la misma
institución. /usuarios/me/campanas filtra por la relación del usuario autenticado
directamente en la consulta del repositorio. No se devuelven miembros, correos ni saldos.

Las rutas HU29 también verifican pertenencia para campañas: catálogo, detalle,
unión y progreso. Unión/progreso bloquean el vínculo durante su transacción para
evitar aceptar una revocación concurrente entre autorización y guardado. El catálogo
sin identidad solo devuelve retos globales y el detalle sin identidad rechaza campañas.
Las participaciones históricas propias continúan accesibles como información del usuario.

## API

Authorization: Bearer JWT en todas las rutas. Content-Type application/json en POST.

`POST /instituciones/{institucionId}/campanas`

```json
{
  "nombre":"Movilidad limpia",
  "objetivo":"Agrupar trayectos y elegir movilidad sostenible",
  "fechaInicio":"2026-11-01",
  "fechaFin":"2026-11-07"
}
```

Fechas ilustrativas: ajustarlas al día actual o posterior. Nombre y objetivo son
obligatorios, no pueden ser espacios y admiten como máximo 255 caracteres cada uno,
compatibles con las columnas de Reto. Fechas ISO yyyy-MM-dd obligatorias, inicio no
anterior al día del servidor, fin >= inicio y año <= 9999 para interoperabilidad SQL/JSON.
La duración cuenta ambos días: inicio=fin significa una campaña de un día. La fecha fin
permite participación hasta ese día inclusive, como HU29. No hay un máximo comercial
de duración inventado. No existe publicación en borrador en esta historia.

HTTP 201, Location: /instituciones/5/campanas/50 (IDs ilustrativos):

```json
{
  "id":50,
  "institucionId":5,
  "nombre":"Movilidad limpia",
  "objetivo":"Agrupar trayectos y elegir movilidad sostenible",
  "fechaInicio":"2026-11-01",
  "fechaFin":"2026-11-07",
  "duracionDias":7,
  "publicada":true,
  "estado":"FUTURA",
  "seguimiento":{
    "retoId":50,"titulo":"Movilidad limpia",
    "fechaInicio":"2026-11-01","fechaFin":"2026-11-07",
    "participantes":0,"progresoColectivo":0,
    "estado":"NO_DISPONIBLE","fechaCierre":null
  }
}
```

GET, sin body:

- `/instituciones/{institucionId}/campanas?pagina=0&tamano=20`: lista institucional.
- `/instituciones/{institucionId}/campanas/{campanaId}`: detalle y seguimiento HU29.
- `/usuarios/me/campanas?pagina=0&tamano=20`: campañas de todas las instituciones vinculadas.

Las listas incluyen futuras, activas y finalizadas; se ordenan por inicio e ID
descendentes, con pagina >= 0 y tamano entre 1 y 50. HTTP 200, lista vacía [] cuando
no haya resultados. Estado de campaña: FUTURA, ACTIVA, FINALIZADA o NO_DISPONIBLE
si activo=false. El campo seguimiento conserva los estados y resultados HU29:
antes del inicio NO_DISPONIBLE; después del periodo PENDIENTE_CIERRE hasta el job,
y luego EXITOSO o NO_ALCANZADO. Publicada=true no permite unirse antes del inicio.

El frontend puede comprobar el acceso al formulario mediante la ruta existente
`GET /instituciones/{id}/administracion` de HU51. No se implementa HTML ni otro endpoint
que simule un formulario.

## Participación y cierre HU29

- `GET /retos/colectivos`: retos globales disponibles más campañas disponibles del miembro.
- `GET /retos/colectivos/{id}`: resumen autorizado para miembros de la campaña.
- `POST /retos/colectivos/{id}/unirse`, sin body: inscripción explícita, HTTP 201.
- `PUT /retos/colectivos/participaciones/{participacionId}/progreso`
  con `{"progreso":50}`: HTTP 200. Solo participación propia y afiliación vigente.

Se conservan media aritmética, bloqueo por reto, restricción de participación única,
fechas y resultados persistidos. El job existente cierra los colectivos vencidos sin
necesitar JWT ni pertenencia de un usuario ficticio. Cerrar conserva el evento HU37.
No hay inscripción automática ni puntos, niveles o insignias adicionales.

HU35/HU36 no se modifican. HU44 continúa permitiendo compartir explícitamente un logro
propio verificado, incluido un colectivo exitoso: publica el título del logro según la
privacidad comunitaria, sin dar acceso al objetivo o administración de la campaña.

## Errores

JSON con mensaje y, para validaciones de campos, lista errores. 400 por campos, fechas,
IDs o paginación inválidos; 403 por falta de vínculo/rol institucional; 404 por institución
o campaña inexistente en esa institución; 409 por duplicado/conflicto concurrente;
500 por persistencia/transacción sin detalles internos. La seguridad JWT existente
responde 403 sin autenticación o con token inválido; el servicio rechaza identidad nula.

```json
{"mensaje":"No tienes acceso administrativo a esta institución"}
```

```json
{"mensaje":"Ya existe una campaña con ese nombre y periodo en la institución"}
```

## Migración V4

`db/migration/V4__campanas_institucionales.sql`: nueva columna nullable retos.institucion_id,
FK sin cascada destructiva, CHECK de campaña colectiva válida/sin recompensa ni origen HU35,
índice de consulta y unicidad por institución/nombre normalizado/periodo.
Los retos históricos conservan NULL y su comportamiento original.

También amplía el CHECK de rol en usuarios_instituciones: reemplaza únicamente los CHECK
de la columna rol que contienen ADMIN_INSTITUCIONAL por el conjunto ADMIN_INSTITUCIONAL,
MIEMBRO. Es necesario porque Hibernate pudo generar el CHECK anterior. Se hace dentro
de la transacción, sin cambiar ni borrar afiliaciones, claves o tablas. Un dato incompatible
aborta la migración y revierte sus cambios. La duración no se valida contra CURRENT_DATE
en el CHECK para que los registros históricos sigan siendo válidos al pasar los días.

El proyecto no declara Flyway/Liquibase ni configuración de ejecución de esas herramientas.
Los scripts de db/migration requieren aplicación manual controlada; no se ejecutaron.
Revisar V1/V2/V3/V4 y respaldo antes de aplicar V4 exclusivamente en la base aislada,
con la aplicación detenida. Después verificar el arranque mediante ddl-auto=validate
en la configuración de ejecución, sin editar application.properties.

## Preparación y verificación manual

Se necesitan dos instituciones, un administrador de cada una, un miembro MIEMBRO de
la primera y un usuario externo. HU51 permite registrar institución y su administrador;
no existe todavía un endpoint general de afiliación de miembros. La relación MIEMBRO
de prueba debe prepararla el responsable de la base de forma controlada; HU54 no ofrece
un atajo público para afiliarse ni crea usuarios o afiliaciones ficticias. No usar datos
importantes de la base principal para estas pruebas.

1. Confirmar base aislada y migraciones aplicadas. Obtener JWT propios.
2. Crear campaña con JWT del administrador de esa institución: 201 y Location.
3. Repetir nombre/periodo: 409. Cambiar institución con el otro administrador legítimo:
   puede crear su propia campaña; el primero recibe 403 en esa institución ajena.
4. Probar miembro ordinario y externo creando: 403. Sin JWT: 403. Probar blancos,
   campos omitidos, fecha imposible, inicio pasado y fin anterior: 400.
5. Consultar listas/detalle con administrador y miembro: 200. Externo u otro administrador:
   403. Probar detalle con ID de campaña perteneciente a otra institución: 404/403 según ruta.
6. Comprobar /usuarios/me/campanas: solamente instituciones vinculadas. En catálogo HU29
   las campañas ajenas no aparecen y no pueden consultarse/unirse adivinando su ID.
7. Crear con inicio hoy para participar; una futura aparece como FUTURA pero rechaza unión.
   Unirse dos veces: 201/409. Actualizar progreso propio por HU29; el externo se rechaza.
8. Para cierre natural, usar campaña de un día y comprobar tras vencer el periodo el
   resultado del job existente. No existe endpoint para cerrar antes ni se cambia el reloj.
9. Comparar puntos/niveles, participaciones previas, fuentes HU35/HU36 y publicaciones HU44:
   crear/consultar campaña no los modifica. El cierre conserva el refresco HU37 de HU29.
10. Enviar dos creaciones simultáneas del mismo nombre/periodo: solo una campaña,
    una respuesta 201 y otra 409. La suite simula el bloqueo; verificarlo también en PostgreSQL.

```sql
SELECT current_database();
SELECT id, nombre FROM public.instituciones ORDER BY id;
SELECT id, usuario_id, institucion_id, rol, fecha_afiliacion
FROM public.usuarios_instituciones ORDER BY institucion_id, usuario_id;

SELECT id, institucion_id, titulo, descripcion, tipo, activo, fecha_inicio, fecha_fin,
       puntos_recompensa, usuario_recomendacion_ia_id
FROM public.retos WHERE institucion_id IS NOT NULL ORDER BY id;

SELECT r.institucion_id, r.id AS campana_id, ur.usuario_id, ur.estado, ur.progreso,
       rc.estado AS resultado, rc.participantes, rc.progreso_final, rc.fecha_cierre
FROM public.retos r
LEFT JOIN public.usuarios_retos ur ON ur.reto_id = r.id
LEFT JOIN public.resultados_retos_colectivos rc ON rc.reto_id = r.id
WHERE r.institucion_id IS NOT NULL ORDER BY r.id, ur.id;

SELECT institucion_id, lower(btrim(titulo)), fecha_inicio, fecha_fin, count(*)
FROM public.retos WHERE institucion_id IS NOT NULL
GROUP BY institucion_id, lower(btrim(titulo)), fecha_inicio, fecha_fin HAVING count(*) > 1;

SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
WHERE conrelid IN ('public.retos'::regclass, 'public.usuarios_instituciones'::regclass);
SELECT indexname, indexdef FROM pg_indexes WHERE schemaname='public' AND tablename='retos';
```
