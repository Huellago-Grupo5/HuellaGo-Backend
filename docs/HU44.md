# HU44: compartir logros ambientales

HU44 añade publicaciones explícitas de insignias obtenidas y retos completados.
No existía una tabla de publicaciones ni un espacio comunitario implementado por
HU41/HU42/HU43. Se reutilizan Usuario, Insignia, UsuarioInsignia, UsuarioReto, Reto,
ResultadoRetoColectivo y la preferencia visibilidadComunidad de HU48.

## API

Todas las rutas requieren el JWT y la sesión activa existentes.

`POST /comunidad/publicaciones`, Content-Type application/json:

```json
{"tipo":"INSIGNIA","origenId":8}
```

Para INSIGNIA, origenId es el ID de catálogo devuelto por GET `/usuarios/me/insignias`;
el servidor verifica la asignación obtenida y su fecha en usuarios_insignias.

```json
{"tipo":"RETO","origenId":9}
```

Para RETO, origenId es el ID de participación usuarios_retos, NO el ID del reto.
Se verifica su propietario usando exclusivamente la identidad JWT.
No se aceptan cantidades de puntos, títulos ni afirmaciones de finalización del cliente.

Ejemplo de confirmación HTTP 201 (IDs y fecha ilustrativos):

```json
{
  "mensaje":"Logro publicado en la comunidad",
  "publicacion":{
    "id":1,"autorId":77,"autor":"Ana","tipo":"INSIGNIA","origenId":8,
    "titulo":"Primer paso verde","fechaPublicacion":"2026-10-24T12:00:00"
  }
}
```

`GET /comunidad/publicaciones?pagina=0&tamano=20`, sin body, devuelve HTTP 200 y
una lista de DTO de publicaciones, ordenada por fecha e ID descendentes.
pagina >= 0; tamano entre 1 y 50. Una página sin publicaciones devuelve [].
La respuesta usa Cache-Control: no-store para evitar reutilizar respuestas con visibilidad anterior.

Errores JSON contienen `mensaje`: 400 por JSON/tipo/ID/paginación inválidos;
403 por insignia no obtenida; 404 por insignia inexistente, usuario inexistente o
participación inexistente/ajena; 409 por duplicado, conflicto concurrente o finalización
no acreditada; 500 por fallo de persistencia/transacción sin detalles internos.
Sin JWT o con JWT inválido se conserva el HTTP 403 de la seguridad del proyecto.

## Evidencia de finalización

- Insignias: asignación propia en usuarios_insignias y fechaObtencion no nula.
- Retos individuales: participación propia, estado completado, progreso 100 y fechaCompletado.
- Colectivos: participación propia con progreso 100 y estado activo/completado,
  más resultado persistido EXITOSO, progreso final 100 y fechaCierre. HU29 conserva
  el estado activo de las participaciones tras el cierre: se usa el resultado del grupo
  como evidencia, sin modificar HU29. Antes del cierre, con NO_ALCANZADO o participación
  cancelada/incompleta no se puede compartir como reto completado.

No se publican por esta historia recomendaciones completadas de HU36, saldos o niveles.
Un reto personal HU35 es compartible una vez completado por HU24.

## Persistencia, privacidad y compatibilidad

Nueva tabla publicaciones_comunitarias: ID, FK autor, FK insignia o participación,
título copiado del logro real y fecha del servidor. El título es una instantánea,
sin texto libre adicional enviado por el cliente.

La operación es transaccional. Primero se bloquea el usuario con el mecanismo ya
existente; luego se valida la evidencia y se guarda. No se llaman servicios de
recompensas, finalización, recomendaciones o eventos de HU37.
Una insignia se comparte una vez por autor; una participación se comparte una vez.
Los índices únicos respaldan esta regla ante concurrencia. Dos usuarios pueden
compartir la misma insignia si ambos la obtuvieron.

Con visibilidadComunidad=true, terceros ven ID y nombres del autor; no reciben
apellidos, correo, contraseñas o tokens. Con false o null, ven `Usuario privado`
y autorId/origenId nulos. El autor puede ver su propia identificación.
La preferencia se lee al consultar, no se copia en la publicación: cambiar a privado
limita también la identidad en publicaciones previas. El logro compartido explícitamente
y su título siguen visibles de forma anónima; no se vuelve pública la cuenta.

## Migración V3

Archivo: db/migration/V3__publicaciones_comunitarias.sql. Revisar y aplicar manualmente
después de V1/V2, primero en una base aislada. No se ejecutó durante la implementación.
No hay nuevas dependencias ni cambios de application.properties.

El SQL es transaccional y permite reejecución: crea la tabla si falta, completa FKs y
CHECK de un único origen y título no vacío, índices únicos y el índice de consulta.
No elimina datos ni cambia las tablas históricas. Si hay datos incompatibles en una
tabla previamente creada, falla y revierte. Los tipos corresponden al mapeo JPA.
Después de la aplicación controlada, iniciar con ddl-auto=validate mediante la
configuración de ejecución; no usar update para sustituir la migración.

## Pruebas manuales en la base aislada

No utilizar estas operaciones de escritura en huellagodb. Elegir logros reales
de usuarios independientes y registrar los valores previos de puntos/nivel/participaciones.

1. Con JWT del autor, GET `/usuarios/me/insignias`; elegir una con desbloqueada=true y fechaObtencion.
2. POST `/comunidad/publicaciones` con tipo INSIGNIA y su ID. Esperar 201.
3. GET `/comunidad/publicaciones`: comprobar publicación y fecha.
4. Repetir POST: 409; sigue existiendo una sola fila.
5. Compartir una participación individual completada con tipo RETO: 201.
6. Intentar una participación ajena/inexistente: 404; activa/incompleta: 409.
7. Probar una participación colectiva de un grupo cerrado EXITOSO con progreso
   propio 100: 201. Usar un NO_ALCANZADO o grupo todavía abierto: 409.
8. Sin JWT o con token inválido: 403. Probar tipo desconocido, origenId negativo,
   fraccionario o campos omitidos: 400 con mensaje.
9. Desde un JWT distinto consultar la publicación antes y después de usar
   PUT `/usuarios/me/preferencias/privacidad` del autor con
   `{"visibilidadComunidad":false}`. Comprobar alias y ausencia de autorId/origenId.
10. Enviar dos POST simultáneos sobre un logro aún no compartido: uno 201 y otro
    409. Verificar una fila. No se otorgan eco-puntos por ninguno de estos POST.
11. Verificar que recomendaciones HU35/HU36, vínculos, participaciones y resultados
    HU29 conservan los valores previos; no se disparan refrescos de HU37 al compartir.

```sql
SELECT current_database();

SELECT id, usuario_id, insignia_id, fecha_obtencion
FROM public.usuarios_insignias WHERE usuario_id = 77;

SELECT ur.id, ur.usuario_id, ur.reto_id, r.tipo, ur.estado, ur.progreso,
       ur.fecha_completado, rc.estado AS resultado_grupal, rc.progreso_final, rc.fecha_cierre
FROM public.usuarios_retos ur JOIN public.retos r ON r.id = ur.reto_id
LEFT JOIN public.resultados_retos_colectivos rc ON rc.reto_id = r.id
WHERE ur.usuario_id = 77;

SELECT id, autor_id, insignia_id, usuario_reto_id, titulo, fecha_publicacion
FROM public.publicaciones_comunitarias ORDER BY fecha_publicacion DESC, id DESC;

SELECT autor_id, insignia_id, COUNT(*) FROM public.publicaciones_comunitarias
WHERE insignia_id IS NOT NULL GROUP BY autor_id, insignia_id HAVING COUNT(*) > 1;

SELECT usuario_reto_id, COUNT(*) FROM public.publicaciones_comunitarias
WHERE usuario_reto_id IS NOT NULL GROUP BY usuario_reto_id HAVING COUNT(*) > 1;

SELECT id, eco_puntos, nivel, visibilidad_comunidad FROM public.usuarios WHERE id = 77;

SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
WHERE conrelid = 'public.publicaciones_comunitarias'::regclass;
SELECT indexname, indexdef FROM pg_indexes
WHERE schemaname = 'public' AND tablename = 'publicaciones_comunitarias';
```

Sustituir 77 por el usuario independiente de pruebas. No se ha accedido a PostgreSQL
durante el desarrollo. Las pruebas usan MockMvc, repositorios simulados y transacciones
de Spring sin recursos externos. Concurrencia y rollback se verifican a ese nivel;
las restricciones y el bloqueo nativo deben comprobarse también en PostgreSQL aislado
después de revisar y aplicar V3. Ejecutar la suite con `mvn test`.
