# HU55: generación de reportes colectivos descargables

## Historia y alcance

EP06. Como administrador institucional, quiero descargar reportes de desempeño
ambiental grupal, para analizar externamente los avances sostenibles de mi organización.

Se revisaron README y la documentación disponible en `docs` (HU37, HU44 y HU54).
HU54 menciona HU55 como funcionalidad futura, pero **no se encontraron criterios de
aceptación oficiales de HU55 ni un formato obligatorio**. No se presentan como oficiales
las siguientes decisiones de implementación, derivadas del alcance solicitado:

- Consulta y descarga autenticadas, exclusivamente para administradores de la institución.
- Datos reales de campañas, participaciones, avances y cierres ya registrados.
- CSV inicial, sin dependencias nuevas, y consulta JSON con los mismos indicadores.
- Validaciones, aislamiento institucional, manejo de reportes vacíos y errores controlados.
- Generación de solo lectura: no crea cierres, participaciones, recompensas ni archivos en la base.

No implementa interfaz visual, reportes individuales de carbono ni indicadores físicos
sin datos verificables. No se calculan CO₂ evitado, árboles, kilogramos reciclados, etc.

## Arquitectura y reutilización

`ReporteInstitucionalController → ReporteInstitucionalService → ReporteInstitucionalServiceImpl
→ InstitucionRepository / RetoRepository / UsuarioRetoRepository / ResultadoRetoColectivoRepository`.

`ReporteInstitucionalCsv` únicamente formatea un `ReporteInstitucionalDTO` ya obtenido.
El controlador utiliza el mismo servicio para JSON y descarga; no hay cálculos alternativos
para cada formato. Cada petición obtiene su propia instantánea: dos peticiones separadas
pueden diferir si entre ambas se registraron avances o cierres legítimos.

Se reutilizan las tablas existentes:

- `instituciones`: ID y nombre. No se exportan contacto ni identificador fiscal.
- `usuarios_instituciones`: vínculo y `RolInstitucional.ADMIN_INSTITUCIONAL`.
- `retos`: campañas HU54, tipo `COLECTIVO` e `institucion_id` de la ruta.
- `usuarios_retos`: participación y progreso individual HU29.
- `resultados_retos_colectivos`: instantánea final HU29 por reto.

No se cargan entidades Reto con sus colecciones EAGER: se usan proyecciones escalares,
páginas internas de 250 campañas y agregados por lote. Esto evita multiplicar campañas
por joins y evita cargar nombres, correos o saldos de participantes.

Las reglas puras de seguimiento existentes de HU29 se extrajeron a
`CalculoSeguimientoColectivo`, compartido con HU29 y el estado temporal de HU54.
Se conservan promedio, redondeo, disponibilidad inclusiva y prioridad del cierre.
No se cambian las operaciones de unión, avance, cierre ni recompensas.

## Autorización y consistencia

El filtro JWT existente valida firma, usuario y sesión activa. El controlador recibe
`UserSecurity` y pasa su usuario al servicio; nunca acepta `administradorId` como autoridad.
La ruta indica la institución a consultar, no concede permisos.

`AutorizacionInstitucionalService.exigirAdministradorConsulta` verifica el vínculo exacto
usuario/institución/ADMIN_INSTITUCIONAL mediante el repositorio existente. Un miembro,
un administrador de otra institución y un administrador global sin ese vínculo no pasan.
La autorización utilizada por las operaciones mutantes de HU54 permanece intacta.

La consulta del reporte usa `@Transactional(readOnly=true, isolation=REPEATABLE_READ)`.
Las páginas, agregados y resultados se leen en una misma instantánea PostgreSQL, sin
bloqueos pesimistas ni escrituras. Una revocación o un avance confirmado después del inicio
de la instantánea será visible en una siguiente solicitud, no mezclado con la actual.
La autorización de lectura no usa `FOR SHARE`, incompatible con transacciones PostgreSQL
de solo lectura. Un fallo impide devolver un reporte parcial; no hay datos que guardar o revertir.

Las consultas de campañas y totales comparten el mismo predicado institucional y filtros.
Se construyen mediante Criteria API en fragmentos de los repositorios existentes:
`RetoReporteRepositoryImpl` (selección y conteo de página) y
`UsuarioRetoReporteRepositoryImpl` (conteo total y personas distintas).
`PredicadosReporteInstitucional` añade solo las comparaciones cuyos filtros están presentes.
Las firmas utilizadas por el servicio, DTO, CSV y endpoints no cambian.
Los agregados de avances/cierres reciben únicamente IDs de campañas ya seleccionadas.
Un filtro de campaña se valida contra la institución autorizada y el tipo COLECTIVO;
una campaña ajena se oculta con 404, sin revelar sus detalles.

## API

Base local: `http://localhost:8081`.

| Método | Ruta | Respuesta |
| --- | --- | --- |
| GET | `/instituciones/{institucionId}/reportes/desempeno-ambiental` | JSON |
| GET | `/instituciones/{institucionId}/reportes/desempeno-ambiental/descargar` | Archivo CSV |

Ambas requieren Authorization → Bearer Token → JWT del administrador institucional.
Body → **none**. No requieren `Content-Type` de entrada. `Accept: application/json`
para consulta y `Accept: text/csv` para descarga (opcional; pueden omitirse).
Los errores son JSON también en la ruta de descarga.

Parámetros opcionales, iguales para ambas rutas:

| Parámetro | Tipo | Semántica |
| --- | --- | --- |
| `desde` | fecha ISO yyyy-MM-dd | Incluye campañas cuya fecha fin sea >= desde |
| `hasta` | fecha ISO yyyy-MM-dd | Incluye campañas cuya fecha inicio sea <= hasta |
| `campanaId` | entero positivo | Selecciona una campaña de la institución |

Las fechas definen **solapamiento inclusivo del periodo de campaña**, no una ventana
de eventos individuales ni un recálculo del progreso durante ese intervalo. Se conserva
el seguimiento completo de cada campaña seleccionada. Se puede enviar una sola fecha.
Sin fechas se incluyen todos los periodos disponibles; los filtros JSON quedan `null`.
No se inventa un periodo implícito. Años permitidos: 1–9999; hasta >= desde.
IDs positivos, institución Long y campaña Integer según el modelo.

Ejemplo:

```http
GET /instituciones/1/reportes/desempeno-ambiental?desde=2026-01-01&hasta=2026-12-31&campanaId=6
Authorization: Bearer <JWT_ADMIN_A>
```

## Indicadores y fórmulas

| Campo | Origen / cálculo |
| --- | --- |
| institucion.id/nombre | Institucion existente |
| campaña id/nombre/objetivo/fechas | Reto.id/titulo/descripcion/fechaInicio/fechaFin |
| estado | HU54: NO_DISPONIBLE si no está activa/publicada; FUTURA antes del inicio; FINALIZADA después del fin; ACTIVA dentro del periodo inclusive |
| datos incompletos | Fechas ausentes/invertidas: DATOS_INCOMPLETOS y advertencia; sin rellenarlas |
| participacionesRegistradas | COUNT de filas actuales usuarios_retos por campaña |
| participantes | Cantidad HU29: filas actuales si abierta, cantidad congelada del resultado si cerrada |
| progresoColectivo | HU29: SUM(progreso individual, nulo=0) / cantidad, 2 decimales HALF_UP; 0.00 sin participantes; si existe cierre, progreso_final conservado |
| estadoColectivo | Cierre registrado tiene prioridad; si no: ACTIVO, NO_DISPONIBLE o PENDIENTE_CIERRE conforme HU29 |
| resultadoFinal / fechaCierre | Resultado existente EXITOSO/NO_ALCANZADO y su fecha; null si no se registró cierre |
| totalCampanas | Cantidad de campañas seleccionadas, una por ID |
| futuras/activas/finalizadas/noDisponibles/datosIncompletos | Conteo de estado temporal, categorías excluyentes |
| totalParticipacionesRegistradas | COUNT usuarios_retos para las campañas del filtro, no suma de joins con cierres |
| usuariosParticipantesUnicos | COUNT DISTINCT usuario_id en esas participaciones |
| participacionesConsideradasEnProgreso | Suma de participantes usados por HU29 (incluye snapshots de cierre) |
| progresoGeneralPonderado | SUM(progresoColectivo × participantes) / SUM(participantes), 2 decimales HALF_UP |
| conResultado/exitosas/noAlcanzadas | Conteo de resultados finales registrados, nunca inferidos solo por fechas o avance |

El progreso general es una **métrica descriptiva del reporte**, no una nueva regla de
éxito ni de recompensas. Pondera los promedios de campaña ya redondeados por HU29.
Una persona en dos campañas cuenta como dos participaciones, pero como una persona única.
No se promedian directamente porcentajes de campañas con distinto número de participantes.
Las campañas sin participantes no aportan peso. Si todo el peso es cero, el progreso
general es `null` (no evaluable), no un éxito o fracaso inventado.

Si un snapshot tiene cantidad/progreso nulos o fuera de rango, se conserva en el detalle
y no se publica un progreso general aparentemente fiable. Si difiere la cantidad actual
de participaciones del cierre, se incluye advertencia y se preserva el resultado histórico.
Las restricciones V1/V4 previenen normalmente estos casos; no se corrigen datos al leer.
Los nulos de objetivo/nombre/fecha se representan como null en JSON y celda vacía en CSV.

Vencida no equivale a cerrada: sin resultado, `estadoColectivo=PENDIENTE_CIERRE`,
`resultadoFinal=null` y `fechaCierre=null`. El scheduler HU29, no HU55, hace el cierre.

## Descarga CSV

```http
GET /instituciones/1/reportes/desempeno-ambiental/descargar?campanaId=6
Authorization: Bearer <JWT_ADMIN_A>
```

HTTP 200:

```http
Content-Type: text/csv; charset=UTF-8
Content-Disposition: attachment; filename="reporte-institucional-1-20261025-123000.csv"
Cache-Control: no-store
Access-Control-Expose-Headers: Content-Disposition
```

Se informa Content-Length real. CORS sigue el patrón del proyecto y expone el nombre
descargable al frontend. El cuerpo contiene bytes del CSV, no JSON ni base64.

Características: UTF-8 con BOM, separador coma, finales CRLF, todas las celdas entre
comillas, comillas interiores duplicadas y saltos de línea conservados dentro de la celda
(formato RFC 4180). Decimales con punto, sin formato regional ni porcentajes de texto;
75.00 significa 75%, no 0.75. Fechas ISO. Excel: usar Datos → Desde texto/CSV, UTF-8 y
delimitador coma si la configuración regional no lo reconoce al abrir directamente.
Es CSV, **no PDF ni XLSX nativo**.

Hay 33 columnas, en este orden:

```csv
"tipo_fila","institucion_id","institucion_nombre","generado_el","filtro_desde","filtro_hasta","filtro_campana_id","total_campanas","campanas_futuras","campanas_activas","campanas_finalizadas","campanas_no_disponibles","campanas_datos_incompletos","total_participaciones_registradas","usuarios_participantes_unicos","participaciones_consideradas_en_progreso","progreso_general_ponderado_porcentaje","campanas_con_resultado","campanas_exitosas","campanas_no_alcanzadas","campana_id","campana_nombre","objetivo","fecha_inicio","fecha_fin","estado_campana","estado_colectivo","participaciones_registradas_campana","participantes_seguimiento","progreso_colectivo_porcentaje","resultado_final","fecha_cierre","advertencias"
"CAMPANA","1","Institución de prueba","2026-10-25T12:30","","","6","1","0","1","0","0","0","1","1","1","50.00","0","0","0","6","Reciclaje en Equipo HU54","Reducir residuos en equipo","2026-10-25","2026-11-25","ACTIVA","ACTIVO","1","1","50.00","","",""
```

La fila es ilustrativa. Los totales institucionales se repiten como contexto en cada fila;
**no deben sumarse entre filas en Excel**. Las filas CAMPANA son una por campaña.
Las advertencias se unen con ` | ` y también se escapan.

Sin campañas se conservan la cabecera y una fila `RESUMEN_SIN_CAMPANAS`, con metadatos,
totales cero, progreso general vacío y columnas de campaña vacías. JSON devuelve
`campanas: []` y advertencia. Ambos son HTTP 200: reporte válido sin registros, no 404.
Con campañas sin participantes: participantes=0, progresoColectivo=0.00, sin inventar cierre.

Protección de fórmulas: todos los textos se examinan antes del escapado. Si comienzan
con `=`, `+`, `-` o `@` (incluso tras espacios, controles o caracteres de formato), o con
tabulación/CR/LF, se antepone apóstrofo. Las comillas CSV solas no son protección.
La neutralización solo afecta la exportación, nunca el texto almacenado o el JSON.
No se exportan nombres de miembros, correos, contraseñas, JWT, eco-puntos ni niveles.

## Errores

| HTTP | Caso |
| --- | --- |
| 200 | JSON/CSV válidos, incluso sin campañas o sin participaciones |
| 400 | ID no positivo/mal formado/fuera del tipo, fecha imposible, año fuera de rango o periodo invertido |
| 403 | Sin vínculo ADMIN_INSTITUCIONAL; también sin JWT/inválido/expirado/sesión cerrada según seguridad JWT existente |
| 404 | Institución inexistente; campaña inexistente, no colectiva o ajena a la institución |
| 500 | Error inesperado de lectura, transacción o generación, sin filtrar SQL ni información interna |

Ejemplos:

```json
{"mensaje":"No tienes acceso administrativo a esta institución"}
```

```json
{"mensaje":"Campaña no encontrada en esta institución"}
```

```json
{"mensaje":"No se pudo generar el archivo del reporte"}
```

Los errores del controlador son JSON y no incluyen Content-Disposition de archivo.
La seguridad existente rechaza antes del controlador; su 403 no garantiza el mismo
DTO de error. No se cambia globalmente a 401 para no modificar historias anteriores.
No se usa 409 porque exportar no crea un conflicto de negocio.

## Migraciones y compatibilidad

**No requiere V5 ni cambios de esquema**: las cinco tablas existentes contienen toda
la información. No se modifican V1–V4, entidades, propiedades, puerto ni dependencias.
El proyecto no declara Flyway/Liquibase; los SQL existentes son scripts de aplicación
manual. No hay que ejecutar ninguna migración por HU55.

No se almacena el CSV ni se deja un archivo persistente en el servidor. No se llama
al cierre de HU29, a HU37 ni a métodos mutantes. HU35/HU36 mantienen sus vínculos,
estados y fechas; HU44 sus publicaciones; HU54 sus campañas. Los puntos, niveles e
insignias no intervienen en los cálculos del reporte.

FROM public.instituciones i

WHERE i.id IN (1, 2)

Avance HU29 y cierres por separado (evita multiplicar agregados por joins):

```sql
SELECT r.id, r.institucion_id, COUNT(ur.id) AS participaciones,
       CASE WHEN COUNT(ur.id) = 0 THEN 0.00
            ELSE ROUND(SUM(COALESCE(ur.progreso, 0)) / COUNT(ur.id), 2)
       END AS promedio_actual
FROM public.retos r
LEFT JOIN public.usuarios_retos ur ON ur.reto_id = r.id
WHERE r.institucion_id IN (1, 2) AND r.tipo = 'COLECTIVO'
GROUP BY r.id, r.institucion_id
ORDER BY r.institucion_id, r.id;

SELECT rc.reto_id, rc.participantes, rc.progreso_final, rc.estado, rc.fecha_cierre
FROM public.resultados_retos_colectivos rc
JOIN public.retos r ON r.id = rc.reto_id
WHERE r.institucion_id IN (1, 2)
ORDER BY rc.reto_id;

SELECT r.institucion_id, COUNT(ur.id) AS participaciones,
       COUNT(DISTINCT ur.usuario_id) AS personas_unicas
FROM public.retos r
LEFT JOIN public.usuarios_retos ur ON ur.reto_id = r.id
WHERE r.institucion_id IN (1, 2) AND r.tipo = 'COLECTIVO'
GROUP BY r.institucion_id;
```

## Límites y consideraciones pendientes

### Corrección de filtros opcionales (SQLState 42P18)

La consulta inicial utilizaba `(:desde IS NULL OR r.fechaFin >= :desde)` y el mismo
patrón para hasta/campanaId, también en el agregado de participaciones. En el SQL
observado durante la prueba manual, `$2` era la primera aparición de desde, aislada
en `? IS NULL`. PostgreSQL no podía inferir su tipo; el placeholder distinto usado
en la comparación con fecha_fin no tipaba automáticamente ese primer placeholder.
La validación HQL inicial no detectaba este problema de SQL/enlace JDBC.

La corrección elimina esas expresiones, no agrega casts ni parámetros nulos de reemplazo.
Sin filtro no se crea predicado ni enlace; con filtro el valor se compara directamente
con el atributo JPA tipado LocalDate/Integer. La misma construcción se usa para campañas,
conteo de página y totales de participaciones. No cambia el solapamiento inclusivo,
la autorización ni los cálculos. No requiere migración ni cambios de configuración.
