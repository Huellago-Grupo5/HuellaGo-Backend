# HU37: actualización dinámica de recomendaciones

Se reutiliza el motor determinista de HU31. No hay proveedor externo de IA,
tablas nuevas, migración V3 ni nuevas fórmulas de emisiones.

## Disparadores y transacciones

- Registro o modificación válida de hábitos, tras guardar todos sus campos.
- Cálculo inicial y recálculo de huella, tras persistir sus componentes.
- Finalización válida de un reto individual, después del mecanismo de recompensas existente.
- Cierre automático de un reto colectivo: se evalúa a todos sus participantes;
  el resultado grupal no implica que una recomendación individual esté completada.

Los servicios publican `InformacionAmbientalActualizada` dentro de sus transacciones.
El listener `BEFORE_COMMIT` vuelca los cambios y limpia la caché JPA para evaluar
datos actuales. Bloquea los usuarios por ID ascendente antes de generar con HU31;
el generador mantiene el orden ascendente de bloqueos de categorías del catálogo.
El refresco participa en la misma transacción. Un error revierte tanto la operación
original como las nuevas asignaciones; no hay actualización parcial o trabajo asíncrono
pendiente. Las peticiones fallidas o revertidas no disparan evaluaciones persistidas.

No se refresca al editar nombres o correo: HU45 no modifica información ambiental.
Repetir PUT de hábitos con el mismo valor y unidad (ignorando escala decimal, espacios
y mayúsculas) devuelve el registro existente y conserva fechaActualizacion; no invalida
una huella vigente ni publica otro evento.
No se recalcula la huella al editar hábitos ni se infieren nuevos hábitos por completar retos.

## Relevancia y conservación

1. Un cambio de medio, fuente de energía, dieta o hábitos de residuos cambia la
   acción según las ramas existentes de HU31. Cambios numéricos actualizan el motivo.
2. Solo se usa una huella completa, válida y no anterior a los hábitos actuales.
   Las emisiones guardadas determinan la prioridad: todas las categorías empatadas
   en la mayor emisión positiva reciben prioridad ALTA y una acción enfocada
   (agrupar trayectos, revisar equipos encendidos, planificar compras o evitar desechables).
   Se conserva la personalización de la acción base y no se prometen ahorros numéricos.
3. Se considera significativo un cambio que altere la acción aconsejada o la categoría
   de mayor impacto. Si solo varían cifras sin cambiar esas condiciones, se reutilizan
   los mismos IDs de catálogo/asignación y sus fechas. No se establece un porcentaje
   arbitrario de variación total. Esta es una regla cualitativa explícita de HU37.
4. Las recomendaciones completadas (estado o fecha de HU36) y las asignaciones cuyo
   reto personal HU35 ya se completó no se devuelven como sugerencias actuales.
   No se cambia su estado, fecha, vínculo ni participación para lograrlo.
5. Si todas las acciones aplicables ya fueron realizadas, se devuelve
   `SIN_SUGERENCIAS_NUEVAS` con lista vacía; no se inventan nuevas tareas indefinidamente.
6. No se elimina ni archiva ninguna asignación antigua: `POST /generar` devuelve la
   evaluación actual y el historial HU36 conserva las completadas. Los contadores
   históricos de pendientes existentes siguen contando sus estados almacenados.

El catálogo se comparte por categoría y título. El bloqueo del usuario serializa
evaluaciones del mismo propietario; los bloqueos de categorías evitan duplicar
catálogo entre propietarios distintos. HU35 conserva su restricción única publicada.

## API y verificación manual

`POST /usuarios/me/recomendaciones/generar`, Bearer JWT, sin Body: HTTP 200 con
el DTO existente de HU31 (`metodo`, `estado`, `basePriorizacion`, `huellaId`,
`datosFaltantes`, `advertencias`, `recomendaciones`). Una evaluación sin datos suficientes
sigue siendo informativa y no rompe el registro progresivo de hábitos.

Usar una configuración de ejecución que apunte exclusivamente a una base aislada.
No ejecutar estas pruebas de escritura en la base principal.

1. Evaluar dos veces sin cambiar datos: mismos IDs y fechas; ninguna fila duplicada.
2. Cambiar `medio` con PUT `/habitos/{id}` y volver a evaluar: acción coherente con
   el nuevo medio; la huella anterior queda descartada para priorización por antigüedad.
3. POST `/huella-carbono/recalcular`: evaluar de nuevo y comprobar categoría de mayor
   impacto, acción enfocada, prioridad ALTA y desglose del nuevo cálculo.
4. Completar un reto personal de HU35 por sus APIs de progreso/finalización:
   su recomendación origen deja de proponerse sin cambiar su fechaCompletado HU36.
5. Completar una recomendación por HU36 y evaluar: no reaparece como pendiente,
   sigue presente en GET `/usuarios/me/recomendaciones/historial`.
6. Evaluar con dos JWT distintos: ninguna respuesta contiene asignaciones ajenas.
7. Enviar dos evaluaciones simultáneas con el mismo JWT: IDs de asignación estables.
8. Comprobar que el refresco no escribe puntos, niveles, insignias ni participaciones.
   La finalización de retos conserva sus recompensas preexistentes de HU24/HU25.

```sql
SELECT current_database();
SELECT id, usuario_id, recomendacion_ia_id, estado, fecha_generacion, fecha_completado
FROM public.usuarios_recomendaciones_ia
WHERE usuario_id = 123 -- sustituir por usuario independiente de pruebas
ORDER BY id;

SELECT usuario_id, recomendacion_ia_id, count(*)
FROM public.usuarios_recomendaciones_ia
GROUP BY usuario_id, recomendacion_ia_id HAVING count(*) > 1;

SELECT id, usuario_recomendacion_ia_id FROM public.retos
WHERE usuario_recomendacion_ia_id IS NOT NULL;
```

La suite utiliza repositorios simulados y transacciones de Spring sin recursos externos.
Prueba las sincronizaciones BEFORE_COMMIT, rollback y el contrato de serialización
con un bloqueo simulado; el comportamiento del bloqueo nativo y la persistencia real
deben verificarse manualmente en PostgreSQL aislado. No se ejecutan migraciones.
